## The wire

One character attribute:

```
character:SetAttribute("XBotEmote", <a KEY of AnimationIds.Player>)
```

`PS1Animate` reads it and plays the clip **once** at Movement priority through
`AnimationIds.load(animator, "Player", key)`. That loader is mandatory — it
names the Animation `Player/<key>@<uri>`, and PS1Animate's
`animator.AnimationPlayed` guard stops any track whose name does not start with
`Player/` on frame 1. Nothing builds an `Animation` instance by hand.

The attribute is a **pulse, not a state**: `SetAttribute` to the value it
already holds does not fire `GetAttributeChangedSignal`, so the same emote
twice in a row would play once. `EmoteService` clears it to `""` after
`PULSE_SECONDS` (0.25 s), and PS1Animate reads `""` as *released*, never as
*stop* — the empty check comes **before** `stopEmote()` so a release can never
cut a clip that is still running.

**The free dance is untouched.** PS1Animate's `danceOn` latch, the `G` /
`DPadLeft` bind and the `KenopsiaEmote` → `DanceButton` touch path stay exactly
as they were: free, client-local, ungated. Phase 5 adds a *second*,
server-authoritative channel beside it.

## Safety properties (all verified)

- **Zero MarketplaceService calls on a dormant boot.** `armed()` is false, so
  `ownsPassCached` answers "no" without scheduling a probe, `warmPasses` probes
  nothing, and `probePass` refuses an id of `0` anyway. `passById(0)` can never
  match a placeholder row.
- **The one armed web call is `MessagingService:SubscribeAsync`** — a single
  pcall-wrapped subscribe on a spawned thread. In Studio without API access its
  warn is expected.
- **The play path never yields.** Registry decision is pure, the profile read
  is an in-memory table, gamepass ownership comes from a cache warmed on other
  threads. Ownership is never persisted as truth — re-asked every
  `OWNERSHIP_TTL` (120 s) so a refund stops granting within one TTL.
- **All three remotes are rate-gated per player AND per channel**, committed on
  entry (play 1.5 s / equip 0.25 s / shop 2 s). Per channel so a spammed equip
  cannot starve a legitimate play; per player so one client cannot spend
  another's budget. `EmoteEquip` answers with a packet and `ShopPrompt` (once
  armed) spawns a web call, so neither could be left ungated.
- **Lobby predicate is RoomService, not the trial attributes.**
  `KenopsiaActiveTrial` is a *round* flag and `KenopsiaTrialId` is `""` between
  two trials, so only `canonical()` + `isParticipant` is true for a whole match.
  Fails closed: no reference, a malformed room or a throw all read as "not in
  the lobby".
- **Boot order cannot deadlock.** `EmoteService.start` runs after
  `RoomService.start()` (which creates the Remotes folder it waits on) and
  after `Profiles.start()`. Applying Main before EmoteService existed would
  have thrown at require; applying it before the two configs existed would have
  been worse — `WaitForChild` with no timeout, a server that boots to nothing.
  Order 1→5 was followed and each step left the place bootable.
