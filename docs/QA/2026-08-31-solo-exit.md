# QA — Solo exit: alone means back to the main menu (31.08.2026)

User: *"the solo attention does not work. Even if the 2nd Player left and he is
all alone. There is no back to main menu (Kenopsia_DEV). Once the server
notices theres only 1 player in the game, it will just teleport them back to
the main menu. No warning, no countdown. Just directly."*

## Why nothing happened before

Two separate reasons, and both are real:

1. **There was no way back at all.** `grep TeleportService studio-src/` returned
   **zero hits** — nothing in the game had ever teleported anybody anywhere. The
   last player could only sit in a lobby that could never start (the countdown
   needs `MinPlayers`), or close Roblox.
2. **The abort cannot fire in a Studio test.** `removeMember` aborts when
   `remaining < room.requiredMinimum`, and `requiredMinimum` is
   `math.min(#room.members, minPlayers())`. In Studio `minPlayers()` returns
   `Config.Players.StudioTestMinimum = 1`, so with two test clients it is
   `min(2, 1) = 1` and a drop to one player is **not** below it. In production
   (`MinPlayers = 2`) it does fire — so a Studio two-client test would show
   exactly the "solo attention does not work" the user saw.

The new behaviour is population-based and sidesteps (2) entirely.

## What shipped

**NEW `Services/SoloExit.luau`**, started from `Main` right after `Lobby`:
on `PlayerRemoving`, if exactly one player remains, that player is teleported
straight to **Kenopsia_DEV `129909297895850`** (the MainMenu place, same
universe `10640788131`). No message, no countdown, no key — `TeleportAsync`
immediately.

Runs in **every phase**, not just during a match: two in the lobby and one
leaves, the other cannot play either and goes back the same way.

### The one deliberate narrowing — and why it matters

The trigger is **a departure**, not the head count.

A fresh server *always* has exactly one player: the first to arrive. If the
rule were simply "one player ⇒ send to the menu", every arrival would be
bounced back instantly, the menu would send them out again, and the two places
would ping-pong forever — nobody could ever wait for a second player. So the
check runs only when somebody **leaves** and exactly one is left standing,
which is precisely the reported case ("the 2nd Player left and he is all
alone").

A player who joins alone still waits in the lobby, as before.

### Safety

- `remainingAfter(leaving)` subtracts the leaving player explicitly —
  `PlayerRemoving` fires while they are *still* in `Players:GetPlayers()`, so
  counting the list directly would be off by one.
- Per-user `sending` latch: no double teleport.
- `BindToClose` sets `closing`, so the head count passing through 1 during
  shutdown does not fire a pointless teleport.
- `TeleportInitFailed` clears the latch and warns; the player simply stays, and
  the existing abort/lobby behaviour is the fallback.
- In Studio the call is skipped with a printed line instead of throwing —
  `TeleportService` does not run there.

14/14 green.

## Still needs production (test debt)

`TeleportService` does not work in Studio, so **the teleport itself has only
been verified up to the call**. The first published two-player test is what
proves the landing in Kenopsia_DEV. If the id is ever wrong it is one line —
`SoloExit.MENU_PLACE_ID` — and the boot log prints it every start.
