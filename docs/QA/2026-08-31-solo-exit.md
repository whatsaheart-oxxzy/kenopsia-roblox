# QA — Solo exit: alone means back to the main menu (31.08.2026)

User: *"the solo attention does not work. Even if the 2nd Player left and he is
all alone. There is no back to main menu (Kenopsia_DEV). Once the server
notices theres only 1 player in the game, it will just teleport them back to
the main menu. No warning, no countdown. Just directly."*

## Why nothing happened before

Two separate reasons, and both are real:

1. **There was no way back at all.** `grep TeleportService studio-src/` returned
   **zero hits** — nothing in the game had ever teleported anybody anywhere. The
   last player could only sit in a lobby that could never start (the countdown
   needs `MinPlayers`), or close Roblox.
2. **The abort cannot fire in a Studio test.** `removeMember` aborts when
   `remaining < room.requiredMinimum`, and `requiredMinimum` is
   `math.min(#room.members, minPlayers())`. In Studio `minPlayers()` returns
   `Config.Players.StudioTestMinimum = 1`, so with two test clients it is
   `min(2, 1) = 1` and a drop to one player is **not** below it. In production
   (`MinPlayers = 2`) it does fire — so a Studio two-client test would show
   exactly the "solo attention does not work" the user saw.

The new behaviour is population-based and sidesteps (2) entirely.

## What shipped

**NEW `Services/SoloExit.luau`**, started from `Main` right after `Lobby`:
on `PlayerRemoving`, if exactly one player remains, that player is teleported
straight to **Kenopsia_DEV `129909297895850`** (the MainMenu place, same
universe `10640788131`). No message, no countdown, no key — `TeleportAsync`
immediately.

Runs in **every phase**, not just during a match: two in the lobby and one
leaves, the other cannot play either and goes back the same way.

### The rule, in one line

```
shouldSend(remaining, hadCompany) = hadCompany and remaining == 1
```

It is the **head count** that decides, not who left. Three of four players may
leave without anybody being teleported — only the last one goes back:

| event | remaining | result |
|---|---|---|
| 4 players, 1 leaves | 3 | keep playing |
| 3 players, 1 leaves | 2 | **keep playing** |
| 2 players, 1 leaves | 1 | **back to the menu** |
| the last player leaves | 0 | nothing to do |

### The one deliberate condition — and why it is not optional

`hadCompany`: the server must have actually held two players at some point.

A fresh server *always* has exactly one player — the first to arrive. On a bare
"one player ⇒ send to the menu" rule, every arrival would be bounced back in the
same second, the menu would send them out again, and the two places would
ping-pong forever; nobody could ever wait for a second player and no match could
ever start. `hadCompany` is what makes the head-count rule survivable.

A player who joins alone still waits in the lobby, as before. `hadCompany`
is what separates "I am the last one LEFT" from "I am the first one HERE" —
only the former is a finished game.

### Checked twice, so no path escapes it

The rule is evaluated **on every departure** (the normal case, immediate) and
again **every 5 s by a watch**. The watch exists for one specific failure: if a
teleport fails (network, place offline) the last player would otherwise be
stranded forever, because the retry trigger — somebody leaving — can never come
again; there is nobody left to leave. A 10 s retry floor keeps it from
hammering.

### Safety

- `remainingAfter(leaving)` subtracts the leaving player explicitly —
  `PlayerRemoving` fires while they are *still* in `Players:GetPlayers()`, so
  counting the list directly would be off by one.
- 10 s retry floor between teleport attempts: no double send, no hammering.
- `BindToClose` sets `closing`, so the head count passing through 1 during
  shutdown does not fire a pointless teleport.
- `TeleportInitFailed` warns and the watch retries on its next tick; until it
  succeeds the player simply stays, with the existing abort/lobby behaviour as
  the fallback.
- In Studio the call is skipped with a printed line instead of throwing —
  `TeleportService` does not run there.

## Verified in Play

Console at boot, in order:

```
[Lobby] holding cell ready - spawn at 0, 0.5, 0
[SoloExit] armed - a lone survivor returns to place 129909297895850
```

Decision table exercised live:

| case | remaining | hadCompany | sends? |
|---|---|---|---|
| 4 players, 1 leaves | 3 | yes | no |
| 3 players, 1 leaves | 2 | yes | **no — they play on** |
| 2 players, 1 leaves | 1 | yes | **yes** |
| the last player leaves | 0 | yes | no |
| fresh server, first arrival | 1 | no | no |
| same player after company came and went | 1 | yes | **yes** |

Also verified: a lone player who never had company sat through three watch
ticks (16 s) with the console silent — no misfire. `sendToMenu` throws neither
in Studio nor on `nil`.

`[SoloExit] studio: would send iLoveKilIs to place 129909297895850` confirmed
the exact call the live server will make.

selene on the new module + `Main`: **0 errors, 0 warnings**. Offline battery
14/14 green.

## Still needs production (test debt)

`TeleportService` does not work in Studio, so **the teleport itself has only
been verified up to the call**. The first published two-player test is what
proves the landing in Kenopsia_DEV. If the id is ever wrong it is one line —
`SoloExit.MENU_PLACE_ID` — and the boot log prints it every start.
