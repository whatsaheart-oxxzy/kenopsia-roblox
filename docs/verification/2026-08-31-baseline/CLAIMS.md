## A1-joined-event — PARTIAL (confidence 0.93)

**Finding.** The mechanism the claim describes is real, but two of its words are wrong.

TRUE (confirmed on disk AND in the live place): "Joined" is emitted from inside the spawned profile-load thread in Profiles.onPlayer, after the whole DataStore load loop has finished, and it sits behind a liveness guard. Profiles.luau:227 opens `task.spawn(function()`; :229-254 is the `for attempt = 1, LOAD_ATTEMPTS` load/backoff loop; :258 is `if live[userId] ~= entry or plr.Parent ~= Players then return end`; :261 is `Telemetry.funnel(plr, FUNNEL, 1, "Joined")`. Two further returns inside the loop (:232 on a load that succeeded after the player left, :252 during backoff) also skip it. onLeave nils `live[plr.UserId]` at :276, so the moment PlayerRemoving fires, every one of those guards trips. A player who leaves before the load thread reaches :261 therefore never enters the funnel at all — not even at step 1, the funnel's first step. This is the ONLY join-side analytics call in the game: a game-wide live search of 115 scripts found exactly one `Telemetry.funnel(..., 1, "Joined")` (Profiles:261) and exactly one `AnalyticsService` consumer (Telemetry).

WRONG #1 — terminology: it is not a custom "Joined" *event*. It is funnel step 1 of the funnel `KenopsiaRetention` (Profiles.luau:45 `local FUNNEL = "KenopsiaRetention"`), routed to `AnalyticsService:LogFunnelStepEvent` (Telemetry.luau:104), not to `LogCustomEvent`. Nothing named "Joined" reaches the custom-event stream. Roblox's own engine-side join/session/DAU analytics are untouched by any of this, so early exits are hidden only from THIS funnel, not from analytics generally.

WRONG #2 — causality: a FAILED load does not suppress "Joined". When all three attempts fail, the `for` loop simply ends, execution falls through to the :258 guard, and — if the player is still there — the funnel step fires anyway on the volatile profile. Failure suppresses nothing by itself; it only widens the window. LOAD_ATTEMPTS = 3 with LOAD_BACKOFF = { 2, 5 } (Profiles.luau:42-43) means a fully failing load blocks the fire for at least 7 s of `task.wait` plus three UpdateAsync round trips, versus a few hundred ms on the happy path. So the accurate statement is: load LATENCY (which failure maximises) is the suppression window; a successful-but-slow load hides an exit exactly as well as a failed one, and a failed load with the player still present is fully counted.

Sharpest form of the real problem: the ~7 s failure window coincides almost exactly with the content-warning hold that Profiles' own comment describes — "The boot watchdog holds joiners out for 7 s while the content warning plays" (Profiles.luau:46-47) — i.e. precisely the moment a player is most likely to quit. When the DataStore is healthy, quits during the content warning ARE counted (the load resolves in well under a second). When it is degraded, they silently are not.

Extra defect found while verifying, outside the claim: step 2 is not gated on the load thread. MachineFlow.luau:474-476 fires `Telemetry.funnel(plr, "KenopsiaRetention", 2, "RouletteSeen")` straight off room membership. A player still stuck in the 7 s retry path can therefore be logged at step 2 before step 1, producing out-of-order funnel steps on top of the missing ones.

Live-vs-mirror status for this finding: NOT dependent on the stale client scripts. Both files are server-side, and I read the live place directly — live Profiles:212-270 and :39-49 came back byte-identical to the mirror, as did live Telemetry:100-109. Note however that live-parity.md records that Profiles and Telemetry are not mapped in default.project.json, so their agreement is manual, not tool-maintained.

**Player impact.** None to the player directly — this is analytics-only code that ships dark; no gameplay, UI, or profile behaviour changes either way (the player still gets a fully playable volatile profile on a failed load). The impact is on the developers reading the numbers: because the missing event is step 1 — the funnel's own denominator — every downstream retention ratio (RouletteSeen/Joined, Round1Done/Joined, VerdictSeen/Joined) is computed against a population that has already had its quickest quitters removed, and is therefore inflated. The bias is worst exactly when the game is at its worst (DataStore degraded), so the funnel looks healthiest during the incidents it should be flagging.

## A3-blackscreen-name — CONFIRMED (confidence 0.97)

**Finding.** CONFIRMED, with one qualification the handoff omits: the mismatch is not hidden — LightGuard documents it in its own header.

WHAT THE CODE ACTUALLY DOES. LightGuard.client.luau is a single `task.delay(3, ...)` with no loop and no RenderStepped. Its entire gate is two conditions: (1) `UserInputService.TouchEnabled` (line 33 — desktop returns immediately), and (2) `UserGameSettings.SavedQualityLevel.Value <= 4` (lines 37/39, `LowQualityMax = 4` at line 19). If both hold it raises client-local `Lighting.Ambient`/`OutdoorAmbient` by (14,16,20)/255, sets the attribute `KenopsiaLowLight` (lines 52-54), and fires one RemoteEvent packet whose `event` field is the string `"MobileBlackScreen"` (line 63). Nothing in the file reads a frame, a pixel, a ViewportFrame, a screenshot, or any rendered output — Roblox exposes no such readback. So the claim's two substantive halves are both true: it IS a device/quality heuristic, and it is NOT black-image detection. The name-vs-measurement mismatch is therefore real.

The one payload field that sounds like a measurement, `texMB` (lines 42-48, `Stats:GetMemoryUsageMbForTag(GraphicsTexture)` bucketed to 25 MB steps), is reported only — it never gates the emit. Same for `touch` (line 66), which is structurally always `true` because line 33 already returned otherwise: a constant field in the payload.

QUALIFICATION — the naming is a deliberate, documented choice, not an accident. ## P1-lock-token — CONFIRMED (confidence 0.95)

**Finding.** CONFIRMED, with one precision correction to the wording.

What the code actually does: Profiles DOES write an ownership marker. `tryLoad` stamps `data._lock = { jobId = game.JobId, ts = now }` inside its UpdateAsync transform (Profiles.luau:118). So it is not true that there is *no* marker — there is one. But it is a per-SERVER identity (`game.JobId`), not a per-LOAD token: no GUID/session id is generated per acquisition, so two successive loads of the same player on the same server produce an identical token, and there is nothing that distinguishes "this load" from "a previous load by the same job".

The operative half of the claim is exactly right and is the real defect: `_lock` is read in exactly ONE place in the whole module — `lockHeldByOther` (Profiles.luau:100), which is called only from `tryLoad`. The save path never looks at it. `trySave` (Profiles.luau:129-147) opens an UpdateAsync, blindly copies every OWNED_FIELDS key from the in-memory copy over `stored` (:134-136), and then either nils the lock (`stored._lock = nil`, :138, when release=true) or re-stamps itself as owner (`stored._lock = { jobId = game.JobId, ts = os.time() }`, :140) — in both branches without ever comparing `stored._lock.jobId` to `game.JobId`. There is no compare-and-swap, no abort-if-not-mine, no "someone else took this" telemetry. Verified live: `_lock` occurs at exactly 5 lines in the live MainGame module (91, 100, 118, 138, 140) and the live bytes for lines 96-148 are identical to the mirror.

All four write paths funnel through that unverified `trySave`: the left-while-loading hand-back (:238), PlayerRemoving (:279), the verdict/emote flush (:473), and BindToClose (:649). So an older server whose UpdateAsync is queued or delayed will, when it finally lands, (a) overwrite whatever the newer owner wrote, and (b) if it is a release, delete the newer owner's lock outright — leaving a live-owned profile with `_lock = nil`, loadable by any third server.

Two further source facts make the stale window reachable without inventing a crashed server:
1. The lock's `ts` is refreshed ONLY by a save (:140). There is no heartbeat/renew loop — grep for `_lock` finds no other writer. With `LOCK_STALE_SECONDS = 180` (:41) and flushes occurring only at the verdict (MachineFlow.luau:1325) or an emote grant (EmoteService.luau:260, :278), a profile that is genuinely owned and in play becomes stealable after 3 minutes without a verdict.
2. The menu place and MainGame share universe 10640788131 and the same KenopsiaProfile_v1 store (EmoteService.luau:471-472), and SoloExit teleports players out to the menu place — so MainGame server A -> menu -> MainGame server B is a first-class flow, and it is precisely the flow in which A's in-flight release can land after B has taken ownership.
